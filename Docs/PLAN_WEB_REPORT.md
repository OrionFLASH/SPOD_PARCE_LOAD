# План: web-report — подготовка REPORT из турниров

Локальная веб-страница рядом с `web-edit-full` / `web-fill-full`: загрузка данных по нескольким турнирам, обработка по логике Power Query (FIO + TN в одном контуре), выгрузка CSV и XLSX.

## Решения по неоднозначностям ТЗ (приняты для реализации)

| Вопрос | Решение |
|--------|---------|
| Имя каталога | `common/web-report/` |
| Открытие | Двойной клик по `report_app.html` (`file://`), без сервера — **пересмотрено в 26.46**, было HTTP (`python -m http.server`), как fill-full |
| JSON настроек | Список турниров + параметры; без сырых строк данных (данные — отдельные файлы) |
| Справочник ФИО | `fio_dictionary.json`: `{ version, entries: [{ fio, person_number }] }` |
| Не найдено ФИО | `MANAGER_PERSON_NUMBER` = `00000000` (pad 20), флаг «ТАБЕЛЬНЫЙ НЕ НАЙДЕН» = ДА; UI предлагает дописать справочник |
| Дубли | Ключ `CONTEST_CODE\|TOURNAMENT_CODE\|MANAGER_PERSON_NUMBER`; диалог до финальной выгрузки |
| CSV | Только согласованные строки, 7 колонок |
| XLSX | Все строки + служебные колонки PQ + комментарий по решению дублей |
| Кодировки CSV | UTF-8 (с/без BOM), Windows-1251, CP866 — выбор по эвристике |
| Excel-библиотека | SheetJS (`xlsx.full.min.js`) в папке страницы (офлайн) |

## Поток работы пользователя

1. Открыть страницу → пустая форма или «Открыть JSON настроек».
2. Добавить турниры (параметры вручную).
3. Для FIO: загрузить/вести справочник ФИО↔табельный; сохранить JSON.
4. Загрузить CSV/XLSX → выбрать колонки (ФИО или ТН + показатель).
5. «Сформировать» → предупреждения ФИО → разрешение дублей → скачать CSV/XLSX и JSON настроек.

## UI (волны 26.9+)

Три панели как fill-full: слева турниры и JSON; внизу левой панели — блок «Результат» и конвейер (Проверить → Сформировать → CSV/XLSX); центр — параметры и источник; справочник ФИО при режиме FIO; справа фильтры и компактная сводная статистика. Сверху только этапы и инфо/сводка (без кнопок выгрузки). Копия турнира блокирует работу, пока не сменены код и название. Турниры можно исключать из проверки/выгрузки галочкой.

С **26.19** поля в центре компактнее: высота инпутов ~32px, плотнее сетка; параметры — ряд кодов+период.

С **26.22** сетка **источника** и **ФИО** в три строки:
1. лист Excel + строка угла + колонка угла;
2. колонка ФИО/ТН + колонка показателя (для ФИО: колонка ФИО + колонка табельного + имя файла);
3. действие и число операции слева, имя файла справа (у источника; у ФИО имя файла на строке колонок).

С **26.23** блоки настроек в центре растягиваются на всю ширину области между левой и правой панелями; при скрытии сайдбара центр расширяется.

С **26.25** правая панель фильтров при старте свёрнута, левая (турниры) открыта.

С **26.26–26.28** новый турнир: план = `0`, дата данных = сегодня (локальная); пустые обязательные поля подсвечиваются оранжевым до заполнения.

С **26.29** этапы в шапке: иконка + заголовок + пояснение; состояния done / bad / **idle** (серый). Этап ФИО idle при режиме TN у текущего турнира или если в списке нет FIO-турниров; при отсутствии активных к выгрузке остальные этапы тоже idle.

С **26.31**:
- при проблемах в таблице ФИО — предупреждение + кнопка «Подробнее» → модалка со строками (ФИО, значение ТН, причина, отметка «выбран»);
- кнопка «Загрузить таблицу ФИО» (с иконкой); «Применить» серая и неактивна до загрузки и выбора колонок;
- Проверить / Сформировать / CSV / XLSX и блок результата — только на левой панели (без дублей в центре);
- верхняя панель — этапы + инфо-сводка; справа под фильтрами — карточки статистики (турниры, активные, заполненные, строки, ошибки, CSV, ФИО);
- в карточке турнира после Y/FIO/OK — мини-метрики: всего / с ошибкой / в CSV.

С **26.33**: кнопки конвейера и результат привязаны к низу левой панели (под списком турниров); статистика справа — одна колонка, компактные строки, подсказки `data-tip` при наведении.

С **26.35**:
- JSON настроек хранит `source_file_path` / `fio.file_path`; при открытии JSON страница пытается **сразу** подтянуть CSV/Excel по пути (и запасным вариантам: имя файла, `examples/…`); восстанавливаются лист и колонки.
- Новая ручная загрузка файла источника/ФИО сбрасывает угол на 1,1 и очищает колонки (подсветка «выберите»).
- Сетка источника и ФИО в **одну** строку: лист · стр · кол · колонки (лист уже, угол узкий).
- Превью таблиц сворачиваемое (`<details>`), по умолчанию свёрнуто.

## Справочник ФИО из таблицы (26.24+)

При «Применить» из CSV/Excel:
- дубли по выбранной колонке ФИО → в справочник берётся **первая** строка (сверху вниз), у которой табельный **не пуст и состоит только из цифр** (ведущие нули допустимы);
- если ФИО встречается один раз — берётся как есть (даже с пустым/нечисловым ТН);
- пользователю показывается предупреждение и кнопка «Подробнее» с таблицей проблемных строк и отметкой выбранной.

Пример таблицы: `common/web-report/examples/sample_fio_dictionary.csv`.

## JSON v3 / CSV-гейты (26.16–26.21, 26.35)

- В JSON — только **настройки**: период, fact_op, include, имя файла, **путь** (`source_file_path` / `fio.file_path`), угол, лист, колонки; в блоке `fio` — **entries** (ФИО↔табельный) и метаданные колонок.
- Содержимое CSV/Excel и base64 в JSON **не** сохраняются. Механика автозагрузки по сохранённому пути / имени / `examples/…` в коде сохранена, но с 26.46 страница всегда открыта локально (`file://`) — под этим протоколом браузер не даёт странице читать соседние файлы сама, так что на практике источники после открытия JSON загружают вручную (см. `## Открытие без сервера (26.46)`).
- CSV не выгружается при дублях `MANAGER_PERSON_NUMBER+CONTEST_CODE+TOURNAMENT_CODE`, ТН не из 20 цифр или пустых ячейках; в Excel такие строки помечены в `CSV_ERROR`.
- Диалог дублей: по умолчанию первая строка; нельзя оставить несколько строк одного ключа; при повторной проверке показываются ранее принятые решения (отпечатки строк).

## XLSX: табельный номер всегда текст (26.49)

Раньше документация решала проблему `1.23457E+19` только со стороны источника: «поставьте текстовому столбцу текстовый формат в Excel и загрузите заново» (см. `## JSON v3 / CSV-гейты`, `Docs/WEB_REPORT_USER_GUIDE.md`). Это по-прежнему нужно, если проблема уже в исходном файле — Excel теряет точность числа длиннее 15 значащих цифр физически, на уровне сохранённого файла, до того как файл попадёт в web-report, так что внутри приложения это не восстановить.

Что изменилось — сторона **выгрузки**. Раньше корректность колонки `MANAGER_PERSON_NUMBER` в выходном XLSX держалась только на том, что `padPersonNumber()` всегда возвращает JS-строку, а SheetJS (`aoa_to_sheet`) пишет строковые значения как текстовые ячейки (`t:"s"`) по умолчанию — то есть на неявном свойстве кода, а не на явной гарантии. Теперь это явно и не зависит от типа исходного столбца:

- `ReportCore.PERSON_NUMBER_COLUMNS` — список колонок XLSX-отчёта с табельными номерами (сейчас одна — `MANAGER_PERSON_NUMBER`).
- `ReportIO.forcePersonNumberColumnsAsText(ws, cols, rowCount)` — после построения листа принудительно приводит каждую ячейку этих колонок к тексту: `v` → `String(v)`, `t: "s"`, `z: "@"` (числовой формат «Текстовый»), убирает закешированное отображаемое `w`. Работает независимо от того, что было в ячейке — число или строка.
- `ReportIO.buildReportXlsxWorkbook(rows)` — сборка книги вынесена из `downloadReportXlsx` отдельной чистой функцией (без скачивания), вызывает `forcePersonNumberColumnsAsText`; `downloadReportXlsx` теперь только собирает книгу и скачивает.

Тест `xlsxPersonNumberAsText` (`src/Tests/test_web_report_core.mjs`) собирает книгу из строк с табельным-строкой и табельным-числом и проверяет `t:"s"`, `z:"@"` и `typeof v === "string"` у обеих ячеек через реальный `xlsx.full.min.js`.

## Обновить REPORT (26.48)

Пятый вариант сохранения на левой панели — кнопка **«Обновить REPORT»**, рядом с CSV/XLSX. В отличие от них (собирают файл только из текущей страницы с нуля), эта кнопка **сливает** готовые данные с уже существующим REPORT-файлом: заменяет в нём строки турниров, которые сейчас готовы к выгрузке, не трогая всё остальное.

**Источник исходного REPORT:** файл, загруженный на шаге «Файлы» модалки «Загрузить списки» (если он там был выбран). Весь пакет (`ReportIO` pack — `rows`, `fileName` и т.д.) сохраняется целиком в `state.importedReportPack` перед сбросом транзитного состояния модалки (`runImportTournaments()`, до `resetImportTour()`) — раньше он терялся сразу после импорта турниров. Хранится только в памяти страницы на время сессии: не в JSON настроек, не в `localStorage` (в JSON и так не хранятся сырые строки данных, см. раздел «JSON настроек»).

**Доступность кнопки** (`renderStages()`): `state.importedReportPack` не пуст **и** `state.lastResult.ok` **и** `state.lastResult.csvGate.ok` — то есть ровно тогда, когда CSV реально скачался бы, а не просто кнопка CSV не серая (та выключена лишь при отсутствии `lastResult`; сам гейт при клике может заблокировать модалкой — здесь строже).

**Логика** (`ReportCore.buildReportUpdatePreview` / `applyReportUpdate`, обе чистые и покрыты тестами):

1. Готовые строки (`prepareExportRows().csvRows`, те же 7 колонок REPORT) группируются по `TOURNAMENT_CODE` — набор групп и есть турниры-кандидаты (раз CSV-гейт зелёный, у всех включённых турниров все строки чистые, так что кандидат — каждый турнир с хотя бы одной готовой строкой в этой сессии).
2. Для каждого кандидата — сравнение с тем же `TOURNAMENT_CODE` в `importedReportPack.rows` по `MANAGER_PERSON_NUMBER`: `beforeCount`/`afterCount` (строк было/станет), `removedCount` (табельный был, в новых данных нет), `keptCount` (был и остался), `addedCount` (новый).
3. Турниры, для которых сейчас нет готовых строк, в предпросмотр не попадают и не трогаются — их данные в REPORT остаются как были.
4. Модалка `modal-report-update`: таблица по кандидатам (код, было/станет/ушло/осталось/новых) с чекбоксом у каждого (по умолчанию — отмечены все), «Отметить все» / «Снять все».
5. **«Обновить и скачать»** — `applyReportUpdate(originalRows, newRows, selectedCodes)`: строки отмеченных турниров из исходного REPORT выбрасываются целиком и заменяются новыми; всё остальное (не отмеченные турниры, турниры вне этой сессии) остаётся как было. Порядок: сначала все нетронутые строки, затем новые/заменённые — REPORT не чувствителен к порядку строк.
6. Файл скачивается как `REPORT_<таймштамп>.csv` (`ReportIO.timestampName("REPORT", "csv")` — тот же способ именования, что у обычного CSV-экспорта), тем же форматом (`ReportIO.downloadReportCsv`, значит теми же `CSV_COLUMNS`, `;`, UTF-8 с BOM).
7. После скачивания `state.importedReportPack.rows` заменяется на результат слияния — повторное «Обновить REPORT» в той же сессии работает уже поверх обновлённого файла, а не поверх исходной загрузки.

Модули: `report_core.js` (`groupRowsByTournamentCode`, `buildReportUpdatePreview`, `applyReportUpdate`), `report_app.js` (`openReportUpdateModal`, `renderReportUpdateModal`, персист `importedReportPack`), `report_app.html` (кнопка, `modal-report-update`).

## Чипы фильтров: естественная ширина вместо равных колонок (26.48)

Правка вдогонку к 26.41: сетка `grid-template-columns: repeat(auto-fit, minmax(72px, 1fr))` вела себя по-разному в зависимости от числа чипов и ширины контейнера — в узкой панели фильтров длинные подписи («Содержит», «Только из REPORT») обрезались, а в широкой модалке «Загрузить списки» 2 чипа («Все» / «Только из REPORT») растягивались на половину контейнера каждый (пустые grid-треки `auto-fit` схлопываются, освобождая место оставшимся). Единого значения `minmax` под все контексты не подобрать: короткие подписи (`TN`/`FIO`) не нуждаются в большой ширине, а «Только из REPORT» (~17 символов + иконка) требует ощутимо больше, чем помещается в сайдбар в 3 колонки.

`.chip-row` возвращён на `display:flex; flex-wrap:wrap` (как было до 26.41) — ширина каждого чипа по содержимому, без обрезания и без растягивания; при нехватке места ряд просто переносится на следующую строку. Иконки, единая высота (`min-height:30px`) и отступы (уже добавленные в 26.41) сохранены — внешняя аккуратность не потеряна, только равная ширина колонок, которая и оказалась источником обеих проблем.

## Загрузка списков: только турниры из REPORT (26.47)

На шаге «Статусы» модалки «Загрузить списки», если файл `REPORT` загружен, появляется переключатель **«Какие турниры брать»**:

- **«Все»** (по умолчанию) — прежнее поведение: все строки `SCHEDULE` с отмеченным статусом.
- **«Только из REPORT»** — дополнительный фильтр по присутствию: берутся только строки, чей `TOURNAMENT_CODE` встречается хоть в одной строке загруженного `REPORT` (`ReportCore.buildReportCodeSet`). Полезно, когда нужны не все турниры с нужным статусом, а только те, по которым уже реально есть данные для расчёта.

Без загруженного `REPORT` переключатель не показывается (фильтровать не по чему), `requireInReport` принудительно `false`.

Реализация — новый параметр `options.requireInReport` у `ReportCore.buildTournamentsFromSourceFiles`; фильтр применяется после проверки кода турнира и до проверки на дубль с уже существующими турнирами. Новая статистика `stats.skippedNotInReport` — отражена в live-счётчике на шаге «Статусы» и в итоговом уведомлении после загрузки.

На реальных файлах PROM (23–09/24–09): из 134 турниров, подходящих по статусу, только 58 имеют строки в `REPORT` — заодно у прошедших фильтр почти исчезают предупреждения «дата не найдена в REPORT» (87 → 11), потому что именно они были главной причиной этих предупреждений.

## Открытие без сервера (26.46)

Страница всегда открывается **двойным кликом** по `report_app.html` (`file://`) — заявленное «нужен `http.server`» из первых волн (26.0) пересмотрено: локальная страница должна работать без какого-либо сервера.

Проверено, что реально ломает `file://`, а что нет:

| Механизм | Под `file://` |
|---|---|
| `<input type="file">`, чтение через `FileReader`/`arrayBuffer()` | работает — чисто клиентский API, сети не касается |
| SheetJS (`XLSX.read`/`XLSX.write`) над `ArrayBuffer` | работает — вся обработка в памяти |
| Скачивание CSV/XLSX (`URL.createObjectURL` + `<a download>`) | работает |
| `<script src="report_core.js">` и т.п. | работает — классические `<script>`, не модули; это не `fetch` |
| `fetch("config.json")` | **не работает** — но был запасной вариант со значениями по умолчанию, приложение не ломалось |
| `fetch(url)` для автозагрузки источника/ФИО по пути при открытии JSON | **не работает** — браузер блокирует сетевые запросы со страницы `file:` к соседним файлам; единственная реальная потеря функциональности |

Решения (обсуждено и согласовано с заказчиком):

1. **`config.json` убран.** Значения встроены как `DEFAULT_CONFIG` прямо в `report_app.js` — `loadConfig()` больше не делает `fetch`, просто присваивает объект. Одна точка правды, никакого риска молчаливого расхождения между файлом и кодом.
2. **Автозагрузка источника/ФИО по пути (при открытии JSON) не удаляется, а перестаёт пытаться под `file://`.** `ReportIO.isLocalFileProtocol()` (`location.protocol === "file:"`) — если да, `tryReadTableFromPaths` сразу возвращает `null`, без попытки `fetch`. Вся остальная механика (кандидаты путей, `source_file_path`/`fio.file_path` в схеме JSON, поле «Путь к файлу») сохранена как задел: если страницу когда-нибудь снова откроют через веб-сервер, автозагрузка заработает сама, без правок кода. На практике сейчас источники после «Открыть JSON» всегда загружают вручную — сообщения об этом (`source_error`, всплывающее уведомление после открытия JSON) переформулированы так, чтобы не звучать как ошибка «не удалось», а прямо объяснять причину («страница открыта локально»).

Затронутые файлы: `report_app.js` (`loadConfig`, сообщения после открытия JSON), `report_io.js` (`isLocalFileProtocol`, guard в `tryReadTableFromPaths`), `config.json` удалён, `ПРАВИЛЬНЫЕ_ИМЕНА.txt` (убраны инструкции про `http.server`). Тест `test_web_report_core.mjs` → `localFileProtocolSkipsAutoload` проверяет, что под `file:` не делается попытка сетевого запроса.

## Фильтры, поиск и инфо-поля источника (26.41)

**Фильтры (правая панель):** к «Тип расчёта» и «Готовность» добавлен блок **«В выгрузке»** — чипы «Включены» / «Выключены» по флагу `include_in_report`, независимо от готовности. Все чипы (тип, включение, готовность, режим поиска) выровнены сеткой `grid-template-columns: repeat(auto-fit, minmax(72px, 1fr))` — одинаковая ширина/высота в ряду вместо произвольного переноса, у каждой кнопки — иконка (переиспользованы иконки этапов из шапки и кнопки «Копировать»).

**Режимы поиска** под строкой поиска — три чипа (единственный выбор):
- **Содержит** (по умолчанию) — совпадение в любом месте поля, как раньше;
- **Начиная с** — совпадение с начала **слова** в поле (не только с начала всего значения): «Герой продаж» находится по «прод»;
- **Целиком** — поле равно введённому тексту полностью.

Поиск идёт по каждому полю (код конкурса, код турнира, название, тип, период) отдельно выбранным режимом, а не по одной склеенной строке — иначе «Целиком» не имело бы смысла.

**Источник данных:** поле «Лист» больше не исчезает у турнира без загруженного файла — показывается неактивным с плейсхолдером «— сначала загрузите файл —» (раньше поле пропадало из сетки, макет прыгал). После загрузки CSV поле по-прежнему скрывается (листов нет), для Excel — активно со списком листов, как раньше.

**«Путь к файлу»** (у источника турнира и у таблицы ФИО) — информационное поле, как «Имя файла»: `readonly`, ручного ввода никогда не предполагалось. Заполняется в двух случаях (26.43):
- **при загрузке файла вручную** — браузер отдаёт только имя файла (реальный каталог ОС недоступен), это имя и сохраняется как путь — им же `tryReadTableFromPaths` пробует найти файл рядом со страницей при следующем открытии JSON;
- **при успешной автозагрузке по пути из JSON** — путь обновляется на `usedPath` (тот кандидат, который сработал).

Если при открытии JSON файл по сохранённому пути (и запасным вариантам — имя, `examples/имя`) не находится, путь **очищается** (не показываем как рабочий), а имя файла остаётся как подсказка, что именно нужно загрузить — вместе с ошибкой источника и пометкой на поле «Лист».

## Загрузка турниров из исходных файлов (26.39)

Кнопка **«Загрузить списки»** на левой панели (рядом с «Открыть JSON» / «Сохранить JSON») открывает модалку в два шага:

1. **Файлы.** Три загрузчика CSV: `SCHEDULE` и `CONTEST` обязательны, `REPORT` — нет (без него дата турниров = сегодня). Каждый проверяется на нужные колонки; при нехватке — красная подсказка под кнопкой, «Далее» неактивна.
2. **Статусы.** Уникальные значения `SCHEDULE.TOURNAMENT_STATUS` — чипы с множественным выбором (счётчик строк у каждого), «Отметить все» / «Снять все», live-счётчик подходящих строк. «Загрузить турниры» неактивна, пока не отмечен ни один статус.

**Сборка турнира** (одна строка `SCHEDULE` с выбранным статусом → один турнир):

| Поле | Источник | Если не найдено / не число |
|------|----------|------|
| `tournament_code`, `contest_code` | `SCHEDULE.TOURNAMENT_CODE` / `CONTEST_CODE` | без кода турнира строка пропускается |
| `period_code` | `SCHEDULE.PERIOD_TYPE` через словарь (`турнир года`→Y, `турнир N квартала`→QN, `турнир <месяц>`→M1–M12) | «Произвольный» (F) |
| `full_name`, `plan_value` | `CONTEST.FULL_NAME` / `PLAN_MOD_VALUE` по `CONTEST_CODE` | конкурс не найден / план пуст или не число → план `0`, имя пустое |
| `contest_date` | самая новая `REPORT.CONTEST_DATE` для этого `TOURNAMENT_CODE` | нет строк в REPORT → сегодняшняя дата |
| `type_ind` | всегда `TN` (источник данных по участникам подключают отдельно) | — |
| `include_in_report` | всегда **`false`** — включают вручную после проверки параметров и загрузки источника | — |

Уже существующие в списке `tournament_code` при повторной загрузке пропускаются (не дублируются). Турнир с хотя бы одним отклонением (конкурс/план/период/дата) получает `import_warning` — в списке слева это фиолетовая рамка и метка «! СПИСКИ» с подсказкой-причиной; поле не сохраняется в JSON настроек (как `source_error`, оно транзитное).

Словарь `PERIOD_TYPE` подобран по реальным выгрузкам PROM (`common/web-report/report_core.js` → `SCHEDULE_PERIOD_TYPE_MAP`); значения вроде «турнир 2 полугодия», «март-июль», «турнир до конца августа» туда не входят и всегда уходят в «Произвольный».

**Попутный фикс (26.39):** определение кодировки CSV (`report_io.js` → `parseCsvBuffer`) сначала пробует строгий UTF-8 (`fatal: true`); раньше эвристика по частоте кириллицы могла ошибочно предпочесть windows-1251 для настоящих UTF-8-файлов без BOM (каждый 2-байтовый UTF-8-символ кириллицы декодируется как два псевдокириллических символа в windows-1251, и счёт получался выше) — так были закодированы файлы `SCHEDULE/CONTEST/REPORT` в `IN/*/SPOD`. Настоящие windows-1251/ibm866 файлы по-прежнему распознаются как раньше (строгий UTF-8 для них не проходит).

## Формат полей выгрузки (26.37)

Согласовано с заказчиком:

| Поле | Формат |
|------|--------|
| `MANAGER_PERSON_NUMBER` | ровно 20 цифр, дополнение нулями слева; не найден (FIO) → 20 нулей |
| `PLAN_VALUE`, `FACT_VALUE` | целая часть, точка, 5 знаков (`100` → `100.00000`); округление, половина — от нуля; отрицательные допустимы (`-10.50000`) |
| `CONTEST_DATE` | `ГГГГ-ММ-ДД` |
| `priority_type` | всегда `1` |

Разбор чисел (`parseNumberStrict`): знак `+ - −`; пробел/NBSP — тысячи; одиночные `,` или `.` — дробная часть; при обоих разделителях дробный — правый (`1.000,25`, `1,000.25`); несколько одинаковых — тысячи (`1.000.000`); `50%` → `0.5`; пусто → `0`.

Не число в колонке показателя (`н/д`, `10 руб`) — **не** ноль: `FACT_VALUE` пуст, в `CSV_ERROR` «показатель не число: «…»», CSV заблокирован, строка считается ошибкой в карточке турнира. План и число операции над показателем должны разбираться — иначе поле подсвечено, турнир не «заполнен».

ТН: в `CSV_ERROR` конкретная причина — экспонента (`1.23457E+19` → задать текстовый формат столбца в Excel), не только цифры, длиннее 20, пуст. Окно «ФИО не найдены» принимает только цифры до 20 знаков.

Excel: числовые ячейки (кроме дат) берутся исходным значением, без формата отображения (`0.123456` при формате `0.00`, `50%` → `0.5`); числа ≥ 1e15 (длинные ТН) — как текст ячейки, чтобы не терять цифры молча.
