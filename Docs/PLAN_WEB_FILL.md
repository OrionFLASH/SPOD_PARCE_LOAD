# Волна 16 — JSON без выдумок, панели, фильтры, каталог

Пожелания и решения зафиксированы в момент постановки; статус — сделано.

## Цель

1. Примеры JSON из PROM-SPOD совпадают с CSV: нет строк и блоков, которых нет в выгрузке.
2. Левая панель скрывается только сама; верхний и нижний колонтитулы остаются.
3. Справа — панель «Поиск и фильтры» (поиск, Турнир/Награда/Архив + новые фильтры), скрывается отдельно.
4. Цвета вкладок понятны без догадок (легенда внизу слева).
5. В edit и fill поля методов/кодов — списки с короткими подписями; `INDICATOR_CODE` — большой список без своего варианта.

## Диагностика — откуда берётся `t_CONTEST_00`

Пример: конкурс `CONTEST_00` («Приветственный»). В CSV `SCHEDULE` для него нет строк, а в старом снимке уже лежал пустой объект `schedule[0]` с `TOURNAMENT_CODE: ""`. Цепочка: экспортер (`export_web_fill_examples_from_spod.py` → `build_contest_data`) при отсутствии строк расписания/индикаторов/групп/наград подставлял пустую строку-заглушку → импорт fill (`expandStoredPrefixedCode`) разворачивал пустое окончание `TOURNAMENT_CODE` в полный код `t_<CONTEST_CODE>` без хвоста → если массив `schedule` пуст, UI сам добавлял `emptyScheduleRow()` (суффикс `P1` + дефолты каталога). В итоге пользователь видел в расписании турнир, которого не было в CSV. То же для `INDICATOR`.

**Правило на весь контур:** чего нет в CSV — в JSON не появляется. Пустой массив `[]`, а не строка с пустыми полями. Новый конкурс «с нуля» в UI по-прежнему может иметь стартовые слоты из каталога — запрет только на импорт/экспорт существующих данных.

## Решения

- **П.1 JSON строго по CSV.** Убрать заглушки в экспортере (нет строк SCHEDULE/INDICATOR/GROUP/REWARD-LINK → `[]`); импорт fill не разворачивает пустой `TOURNAMENT_CODE`/`REWARD_CODE` в `t_CODE`/`r_CODE`, если это единственная пустая заглушка; пустой массив расписания не дополняется `emptyScheduleRow()` при загрузке снимка; `emptyScheduleRow()`/пустой индикатор — только по кнопке «Добавить». Прогон сверки по всем конкурсам `IN/PROM/SPOD` (число строк в JSON = число строк CSV с тем же `CONTEST_CODE`), пересборка всех примеров.
- **П.2 Скрытие левой панели.** `--side-w: 0`, левая колонка исчезает, шаги сверху и подвал снизу остаются.
- **П.3 Правая панель «Поиск и фильтры».** Сетка `левая | workspace | правая`. Слева остаётся: заголовок «Конкурсы», список вкладок, «Добавить/Копировать», легенда. Справа: поиск (режимы «начинается с»/«содержит» по умолчанию/«равно», сравнение с отдельными полями без учёта регистра) и чипы «Турниры/Награды/Архив». Скрытие правой панели независимо от левой; на узком экране панели складываются над/под workspace.
- **П.4–6 Новые фильтры** (внутри группы — ИЛИ, между группами — И):
  - **ПРОМ/ТЕСТ** по `CONTEST_FEATURE.vid` и `CONTEST.TARGET_TYPE` — оба вкл./выкл. значит «не режем по среде», иначе подстрока в любом из двух полей.
  - **Бизнес-блок** по `CONTEST.BUSINESS_BLOCK` / `CONTEST_FEATURE.businessBlock` / `REWARD_ADD_DATA.businessBlock` (ИЛИ): чипы KMMMB, KMKKSB, AKMKKSB, CSM, «Остальные», «Пусто». У товаров ITEM строка смотрит на `ADD.businessBlock`, пусто — наследует блок конкурса.
  - **Статус расписания** `TOURNAMENT_STATUS`: чипы АКТИВНЫЙ/ПОДВЕДЕНИЕ ИТОГОВ/ЗАВЕРШЕН/ОТМЕНЕН/УДАЛЕН, по умолчанию первые три; конкурс виден, если есть хотя бы один период с включённым статусом; нет строк расписания → не проходит (тон «нет турниров» в легенде).
  - **Дата** — один date-picker; конкурс виден, если у хотя бы одного периода дата попадает в `[START_DT, END_DT]`; пустой фильтр не режет, битые/пустые даты периода не матчатся.
  - **Сброс/установить все** внизу правой панели (поиск не трогается).
  - **ITEM: много товаров на одном конкурсе.** В списке слева конкурс — родитель, товары (десятки `REWARD_TYPE=ITEM` на одном `CONTEST_CODE`) — дочерние строки со смещением. Шапка при выбранном товаре: конкурс/индикаторы/группы общие, «Связи + награды» — только этот reward.
- **П.7 Легенда цветов** (приоритет уже был в `contestScheduleListTone`, только подписан): зелёный — есть активный, синий — нет активных, есть подведение итогов, розовый — нет живых, есть завершённые, серый — только отменён/удалён, янтарный — нет турниров/нет ключевых статусов. Компактный столбик внизу левой панели, подсказка с полной формулировкой.
- **П.8–15 Каталог: списки и подписи** (источник — карточки в web-edit/web-edit-full, затем `sync_web_fill_catalog.py`; на чипе fill крупно подпись, мелко код, в CSV уходит код):
  - `INDICATOR_CODE` — `dropdown` вместо `dropdown_custom`, без своего варианта, дефолт `WAIT`; UI — комбобокс с поиском и группировкой по префиксу (`PULMIS_`, `PFIMIS_`, `EFFICIENCYARS…`, `KANBANARS_…_VKS`/`_VKO` и т.д.).
  - `PLAN_METHOD_CODE`: `NOT_USED` (План не задан, новый), `PRESET_VALUE` (Предустановленное, по умолчанию), `DEPENDS_PREVIOUS_PERIOD` (От прошлого периода, было «Вычисляемое»).
  - `PLAN_MOD_METOD`: `MULTIPLIER` (× коэффициент, по умолчанию), `APPEND` (+ число к прошлому, новый).
  - `CONTEST_INDICATOR_METHOD`: `INTEGRAL` → «Интегральный» (по умолчанию), `RELATION` → «Отношение агрегатов» (только подписи).
  - `CONTEST_FACTOR_METHOD`: оставить `FACT` (ручные данные) + добавить `FACT0-FACT1` (Прирост), `RUN_RATE`, `RUN_RATE-FACT1` (Run rate прирост), `FACT0-RUN_RATE1_DOWN` (Run rate отклонение), `RUN_RATE/FACT1` (Run rate % прироста), `FACT0/RUN_RATE1_DOWN` (Run rate % отклонения); длинные формулировки — в `description` и `data-tip`.
  - `FACT_POST_PROCESSING`: `PERCENTILE` (% «лучше чем»), `PERCENTILE_DOWN` (% «попал в»), `PERCENTILE_UPEST` (% «лучше меня»), `PERCENTILE_UP` (% «не хуже»), `SPECIAL_INDICATOR_1` (Уровень группы), `COUNT_BIGGER` (Счётчик лучших); поле по-прежнему `allow_empty: true`.
  - `INDICATOR_ADD_CALC_TYPE`: `NUMERATOR`/`DIVIDER` → «Числитель»/«Знаменатель», сверены edit + fill + full.
  - `INDICATOR_AGG_FUNCTION`: `SUM` (Сумма), `MAX` (Максимум), `MIN` (Минимум), `AVG` (Среднее), `COUNT` (Количество), `COUNT_DISTINCT` (Уник. индикаторы), `COUNT_DISTINCT_CUSTOMER` (Уник. клиенты — раньше ошибочно «сотрудники»), `COUNT_DISTINCT_DEAL` (Уник. договоры), `LAST_VALUE` (Последнее по дате).

# Волна 18 — выбор выгрузки, бизнес-блок, коды ITEM, полный код в JSON, разбиение JS

Код сделан в `web-fill-full`. Однофайловый `web-fill` не зеркалился (как с 16.16). `web-edit-full` затронут только пунктом 18.5 (разбиение JS), без смены поведения каталога. Исходные пожелания — `common/ToDo FILL EDIT.txt`.

## Цель

1. Выгрузить в JSON и CSV не все конкурсы сессии, а выбранные (один или несколько), без новых кнопок скачивания.
2. Бизнес-блок задаётся один раз на листе конкурса; в FEATURE и REWARD — только показ того же значения.
3. Код награды: для обычных типов — `r_` + код конкурса; для **ITEM** — `ITEM_` + окончание товара. Режим «только окончание»/«весь код» как для `r_`/`t_`.
4. В JSON fill поля `TOURNAMENT_CODE` и `REWARD_CODE` хранят полный код; окончание — отдельное поле.
5. Разбить монолитный JS fill-full (и при целесообразности edit-full) на смысловые файлы без смены поведения.

## Точка отсчёта (до волны)

«Сохранить JSON» писал все `contests` + `archive`; «Все 6» — шесть CSV из всех активных конкурсов (архив не входит); в списке слева не было режима отметки, фильтры только прятали строки; бизнес-блок был тремя независимыми полями; коды `r_`/`t_` разворачивались только если код следовал правилу, иначе — целиком; JSON-экспортер клал в `REWARD_CODE`/`TOURNAMENT_CODE` окончание, если код следовал правилу (fill при импорте разворачивал обратно); `game_fill_app.js` был одним файлом ~5.6 тыс. строк, `game_edit_app.js` — ~2.5 тыс., без бандлера (`<script src>` по порядку).

## 18.1 — Выбор конкурсов для JSON и CSV

Кнопка **«Выбрать»** включает режим отметки; рядом компактные иконки «отметить все» (видимые сейчас, с учётом фильтров) и «снять все» (все отметки сессии, включая скрытые фильтром). В режиме выбора у каждой строки конкурса появляется чекбокс; у товаров ITEM отметка только на конкурсе, клик по товару по-прежнему просто открывает карточку. Смена фильтра не сбрасывает выбор — на другом фильтре можно довыбрать, в выгрузку попадает объединение независимо от активного фильтра.

Без новых кнопок скачивания — меняется подпись существующих: «Сохранить JSON» → «Скачать все JSON» / «Скачать выбранные JSON»; «Все 6» → «Скачать все CSV» / «Скачать выбранные CSV» (вторая строка мелким текстом — «все N» / «выбрано K из N»). Архив в JSON: при «все» — как раньше (`contests` + `archive`), при «выбранные» — только выбранные конкурсы, без архива. CSV по-прежнему только активные конкурсы, без архива, фильтр таблиц — по выбранным `CONTEST_CODE`. Пустой выбор в режиме «Выбрать» — файлы не пишутся, toast «Ничего не выбрано».

## 18.2 — Бизнес-блок: один источник

Источник правки — лист «Конкурс», поле `CONTEST.BUSINESS_BLOCK`. На листах FEATURE и REWARD поля `CONTEST_FEATURE.businessBlock` и `REWARD_ADD_DATA.businessBlock` не редактируются (вид locked-value), показывают то же значение, подсказка «Чтобы изменить — задайте бизнес-блок на странице конкурса». При смене на конкурсе значение сразу копируется во `feature.businessBlock` и во все `badges[].add.businessBlock`. В JSON и CSV все три поля по-прежнему присутствуют и заполнены; фильтр списка (16.14) не ломается — после синхронизации три поля совпадают.

## 18.3 — Формат кода награды (в т.ч. ITEM)

Обычные типы (BADGE, LABEL, CRYSTAL, …) — как 16.18, без смены правила: `r_` + `CONTEST_CODE` (+ `_` + окончание, если непустое); если загруженный код не следует принципу — поле целиком; новые пары всегда с префиксом `r_`.

Тип ITEM: полный код — `ITEM_` + окончание (код товара), не `r_`; создание/смена типа на ITEM — префикс `ITEM_` зафиксирован, вводится только окончание; показ уже загруженных — если код начинается с `ITEM_`, слева литерал, справа окончание; без префикса `ITEM_` — поле целиком (старый/чужой формат). Смена типа BADGE→ITEM: если код следовал `r_`+CONTEST_CODE — собрать `ITEM_`+прежнее окончание, иначе не переписывать; ITEM→не-ITEM — аналогично в обратную сторону. Турниры (`t_`) этим пунктом не меняются.

## 18.4 — Полный код в JSON, окончание отдельно

В строке расписания и в связи/награде: `TOURNAMENT_CODE`/`REWARD_CODE` теперь хранят **полный** код, как в CSV SPOD (`t_CODE`, `t_CODE_4001`, `r_CODE`, `ITEM_99`, …); рядом появляются `TOURNAMENT_CODE_ENDING`/`REWARD_CODE_ENDING` — только окончание (нет в CSV SPOD, только JSON fill). CSV-выгрузка из UI по-прежнему пишет полные коды в штатные колонки, без колонок `*_ENDING`. Логика UI читает окончание из `*_ENDING`, если оно есть, иначе вычисляет из полного кода; при правке в UI обновляются оба поля. Старые снимки (окончание в штатном поле, без `*_ENDING`) — если значение похоже на окончание (`isSnapshotCodeEnding`), разворачиваются в полный код как раньше, а вычисленное окончание записывается в `*_ENDING`. Экспортер примеров и тесты `test_web_fill_code_ending.py` переведены на полные коды + `*_ENDING`, `common/examples/web-fill/` пересобран.

## 18.5 — Разбиение JS

## Модель данных JSON

Корень снимка: `version: 5` (расширение v4 fill-full — конкурсы + archive; v2 снимки экспортера мигрируют при импорте), `block` (`PROM`/`PSI`/`MERGED`), `standsManifest` (зарезервировано под IFT без смены схемы), `contests[]`.

Конкурс:

```json
{
  "id": "ex_CONTEST_05",
  "name": "...",
  "stands": ["PROM", "PSI"],
  "data": {
    "contest": { "CONTEST_CODE": "...", "FULL_NAME": "...", "stands": ["PROM"] },
    "feature": { ... },
    "contestPeriod": [],
    "group": [ { "GROUP_CODE": "...", "stands": ["PROM"] } ],
    "indicator": [ { "INDICATOR_CODE": "...", "N": "1", "stands": ["PSI"] } ],
    "schedule": [ { "TOURNAMENT_CODE": "...", "stands": ["PROM", "PSI"] } ],
    "badges": [ { "flat": {...}, "add": {...}, "link": {...}, "stands": ["PROM"] } ],
    "reward_link": []
  }
}
```

Правила: `contests[].stands` — в каких стендах есть этот `CONTEST_CODE` (объединение); `data.contest.stands` — откуда взяты поля карточки (overlap → PROM, массив может быть `["PROM","PSI"]`); каждая строка массивов `group`/`indicator`/`schedule`/`badges` несёт своё поле `stands: string[]`; поле `stands` не уходит в CSV — только метаданные fill, при экспорте CSV отфильтровывается по стенду; новый конкурс в UI получает `stands: ["PROM"]` на конкурсе и всех новых строках.

**Алгоритм merge (приоритет PROM)** — для каждого `CONTEST_CODE` из объединения множеств PROM и PSI:

| Сущность | Ключ строки | Если ключ в обоих | Только PROM | Только PSI |
|---|---|---|---|---|
| contest | `CONTEST_CODE` | данные PROM, `stands: ["PROM","PSI"]` | `["PROM"]` | `["PSI"]` |
| group | `CONTEST_CODE`+`GROUP_CODE`+`GROUP_VALUE` | данные PROM, оба стенда | `["PROM"]` | `["PSI"]` |
| indicator | `CONTEST_CODE`+`INDICATOR_ADD_CALC_TYPE`+`INDICATOR_CODE` | данные PROM, оба стенда | `["PROM"]` | `["PSI"]` |
| schedule | `TOURNAMENT_CODE` | данные PROM, оба стенда | `["PROM"]` | `["PSI"]` |
| reward-link | `CONTEST_CODE`+`GROUP_CODE`+`REWARD_CODE` | link PROM, оба стенда | `["PROM"]` | `["PSI"]` |
| badge (REWARD) | `REWARD_CODE` (через link) | flat/add PROM, если код в обоих; `stands` по link | flat из PROM | flat из PSI |

Union строк: в merged попадают все ключи из обоих стендов (например 5 турниров = 2 PROM-only + 3 PSI-only + общие с победой PROM). REWARD — таблица наград глобальная (не привязана к конкурсу напрямую); в снимок конкурса попадают только `REWARD_CODE`, на которые есть REWARD-LINK этого конкурса.
