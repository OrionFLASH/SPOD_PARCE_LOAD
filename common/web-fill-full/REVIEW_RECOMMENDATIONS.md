# web-fill-full — ревью логики, архитектуры и рекомендации

Дата ревью: 2026-09-25. Код не менялся, документ описывает найденные проблемы и предлагаемые доработки.
Проверено: `game_fill_settings.html`, `game_fill_core.js`, `game_fill_model.js`, `game_fill_filters.js`, `game_fill_ui.js`, `game_fill_io.js`, `game_fill_boot.js`, `catalog.json` / `catalog.js` (идентичны), `README.md`.

Приоритеты: **P1** — теряет или портит данные либо выгружает некорректный CSV; **P2** — логическая ошибка или противоречивое поведение; **P3** — качество, UX, сопровождение.

Пункты с пометкой **[подтверждено]** воспроизведены: модули загружались в Node (vm) с `catalog.json`.

---

## 1. Краткий итог

Функционально контур богатый: стенды, архив с бандлами, коды `r_`/`t_`/`ITEM_`, копирование, выбор для выгрузки. Слабые места сосредоточены в трёх зонах:

1. **Генерация кодов наград** — пары без кода получают одинаковый `r_<CONTEST_CODE>`, и при выгрузке награды молча теряются.
2. **Сериализация CSV/SPOD-JSON** — значения не экранируются, `;` в тексте заменяется на `,`, перевод строки ломает CSV.
3. **Хранение черновика** — черновик может молча удалиться (при смене каталога) или молча перестать сохраняться (переполнение `localStorage`).

С точки зрения архитектуры: 7 скриптов в общем глобальном пространстве с неявным порядком загрузки; модель данных смешана с UI-состоянием и виджетами; JS-тестов нет.

## 2. Критичные ошибки (P1)

### P1-1. Дубли `REWARD_CODE` = `r_<CONTEST_CODE>` → награды пропадают из CSV **[подтверждено]**
- `expandStoredPrefixedCode("")` возвращает голый префикс `r_CC` (`game_fill_model.js:1896-1906`); `expandContestPrefixedCodes` применяет это к **каждой** паре (`:2009-2018`).
- `resyncPrefixedCodes.rewrite("")` делает то же (`:2065-2074`).
- `mountCompositeCode` при простом **открытии** пары с пустым кодом молча записывает `r_CC` (`game_fill_filters.js:90-93`).
- `buildTables` удаляет дубли REWARD по коду: остаётся первая строка (`game_fill_io.js:13`).

Сценарий: новый ТУРНИРНЫЙ конкурс (3 пустые пары) → код `C1` → перезагрузка страницы / «Продолжить черновик» → все 3 пары получают `r_C1`. Выгрузка: **1 строка REWARD и 3 строки REWARD-LINK с одним кодом**. В Node воспроизводится так: `codes: ['r_C1','r_C1','r_C1']`, `REWARD rows: 1`, `LINK rows: 3`. При этом `addPairRow` (`game_fill_ui.js:140-142`) уникальность соблюдает — поведение расходится.

**Рекомендация:**
- пустой код не превращать в голый префикс — либо оставлять пустым, либо сразу выдавать уникальный код через `uniquifyPrefixedCode` с учётом уже занятых;
- `mountCompositeCode` не должен ничего записывать при отрисовке;
- перед экспортом — проверка уникальности `REWARD_CODE` в конкурсе и между конкурсами с понятным отчётом (сейчас дубль между конкурсами тоже молча отбрасывается, `game_fill_io.js:13`).

### P1-2. CSV/SPOD-JSON: нет экранирования, `;` → `,`, перевод строки ломает строку CSV **[подтверждено]**
- `dumpsSpod` оборачивает строку в `"""…"""` без экранирования (`game_fill_ui.js:1159`). Значение, содержащее `"""`, ломает структуру.
- `csvEscape` для JSON-ячеек **заменяет все `;` на `,`** (`:1356-1358`): тексты новостей, `rewardRule`, `feature` и `preferences` молча меняются.
- Перевод строки внутри JSON-ячейки остаётся как есть, без CSV-кавычек: строка CSV обрывается. В Node результат для `{teamNews:"a; b\nc"}` — `{"""teamNews""": """a, b⏎c"""}`.
- Эвристика «это SPOD-JSON» (`:1347-1354`) срабатывает и на обычный текст, содержащий `"""`, `[]` или `{}`.

**Рекомендация:** зафиксировать формат PROM (как именно SPOD ожидает `;`, переводы строк и кавычки внутри строк) и реализовать сериализацию по этой спецификации. Эвристику убрать: тип ячейки известен из каталога (`kind=json` / колонка-оболочка). Если символ нельзя представить в формате, экспорт должен остановиться с сообщением, а не менять данные молча. Добавить round-trip тест: CSV PROM → импорт → экспорт → побайтное сравнение (у Python-стороны уже есть `reconcile_snapshot_with_csv`).

### P1-3. Черновик молча удаляется при смене каталога
`game_fill_io.js:289-299`

Если `catalog_stamp` черновика не совпадает с текущим каталогом, `peekDraft()` **удаляет** `spod_web_fill_full_project_v2`. Каталог меняется при каждом `sync_web_fill_catalog.py` (штамп — `exported_at`), поэтому после обновления каталога вся несохранённая работа пропадает без вопроса.

**Рекомендация:** никогда не удалять молча. Показать на стартовом экране «Черновик от другой версии каталога (дата) — открыть / скачать JSON / удалить».

### P1-4. Ошибка записи в `localStorage` проглатывается
`game_fill_io.js:272-275`

`persistLocal` делает `try{…}catch(_){}`. Полный снимок PROM (`examples/web-fill/contests/spod_fill_all_contests*.json`) весит 3,1–3,6 МБ, а архив хранит полные копии удалённых конкурсов — это близко к лимиту `localStorage` (~5 МБ). После переполнения черновик перестаёт сохраняться, и пользователь об этом не узнаёт.

**Рекомендация:** при ошибке — постоянный баннер «Черновик не сохраняется, выгрузите JSON»; показывать размер черновика; рассмотреть IndexedDB.

### P1-5. Стенд связи отстаёт на один клик от стенда награды
`game_fill_ui.js:236-241` + `game_fill_core.js:477-491`

`getRow()` выполняет `link.stands = b.stands` **до** переключения, после чего `toggleStandInSet` создаёт новый массив для `b.stands`. В итоге связь получает предыдущее значение. `buildTables` фильтрует награды по «badge ИЛИ link», а связи — только по link (`game_fill_io.js:12-14`). Поэтому после снятия PROM с пары связь может уйти в CSV без своей награды (или наоборот).

**Рекомендация:** хранить стенд пары в одном месте (или синхронизировать после toggle в `onUpdated`); в экспорте фильтровать пару целиком.

### P1-6. Нет проверки ссылочной целостности перед выгрузкой
`game_fill_io.js:3-20`

Выгрузка не проверяет, что:
- `REWARD-LINK.GROUP_CODE` есть в GROUP этого конкурса;
- `REWARD-LINK.REWARD_CODE` есть в REWARD;
- в конкурсе нет повторяющихся `GROUP_CODE` / `TOURNAMENT_CODE` (копирование группы копирует и `GROUP_CODE` — `game_fill_model.js:339-352`, текст на `:461` об этом прямо говорит);
- обязательные поля заполнены (`fieldRequirementIssue` в `game_fill_core.js:130` используется только для точки на карточке).

**Рекомендация:** шаг «Проверка перед выгрузкой»: отчёт по конкурсам (ошибки блокируют, предупреждения можно пропустить) со ссылкой на поле.

## 3. Логические ошибки и противоречия (P2)

### P2-1. `REWARD_ADD_DATA` при массовой выгрузке берёт контекст активного конкурса
`game_fill_ui.js:1254-1258`

`addObject` передаёт в `depends_on` `contest: data().contest`, то есть **текущий открытый** конкурс, а не тот, который сериализуется в цикле `buildTables`. Сейчас в каталоге нет полей с `depends_on`, поэтому ошибка скрыта; при первой же зависимости от поля CONTEST выгрузка станет неверной для всех конкурсов, кроме активного.

**Рекомендация:** передавать `d` явно: `rewardRows(d)` → `addObject(add, badge, d)`.

### P2-2. Непоследовательная политика «подставить значение за пользователя»
- `mountChips` — «Не подставляем значение за пользователя» (`game_fill_model.js:2336`);
- `mountSearchCombobox` — при отрисовке молча ставит `variants[0]` (`:2398-2401`, `:2472-2475`);
- `mountDropdownCustom` — ставит `variants[0]` при отрисовке, `change` и `blur` (`:2528-2531`, `:2587-2591`, `:2600-2606`);
- число: пустое обязательное → `default` или `"0"` (`game_fill_filters.js:182`), а при упаковке JSON пустое `number` → `0` (`game_fill_ui.js:1172-1176`), хотя комментарий на `:1240` обещает «без автовыбора значения»;
- `asFiniteNumber(…, 0)` (`:909-921`): нечисловой `period_code` или `criterion_mark_value` молча становится `0`.

В результате в CSV попадают значения, которые никто не выбирал.

**Рекомендация:** одна политика для всех виджетов — пустое обязательное поле остаётся пустым, подсвечивается и блокирует выгрузку через проверку из P1-6.

### P2-3. Потеря ведущих нулей в `INDICATOR_FILTER.filtered_attribute_value`
`game_fill_ui.js:930-932`

Любая строка, похожая на число, превращается в number: `"007"` → `7`, `"1e3"` → `1000`. Для кодов (ТБ, ГОСБ, табельных) это искажение. Тип значения лучше брать из `filtered_attribute_type`, а не угадывать.

### P2-4. Бизнес-блок перезаписывается при импорте
`game_fill_model.js:1795-1805`

`syncBusinessBlockFromContest` вызывается при импорте (`expandContestPrefixedCodes`) и в `contestRow`. Он **перезаписывает** `feature.businessBlock` и `add.businessBlock` значением из `contest.BUSINESS_BLOCK`. Если в PROM они различались, после импорта и экспорта данные изменятся без предупреждения (и без отметки «изменено», потому что потом снимается baseline). Правило «бизнес-блок задаётся на странице конкурса» разумное, но о расхождениях при импорте нужно сообщать.

### P2-5. Стенды: несколько источников истины
- Стенд конкурса задаётся отдельно (`game_fill_core.js:452-463`), но любой клик по стенду строки пересчитывает его как объединение стендов строк (`:464-476`) и затирает ручной выбор.
- `toggleStandInSet` не даёт снять последний стенд и подставляет PROM (`:424-430`): снятие PSI у строки «только PSI» молча превращает её в PROM.
- `STANDS_KNOWN` содержит `IFT`, но в UI и фильтрах его нет (`:8-9`, `:561-571`). Строки только с IFT не видны ни при каком фильтре, кроме «PROM+PSI», и не выгружаются.
- CSV всегда выгружается только для PROM (`CSV_EXPORT_STAND_PROM`, `:11`; `game_fill_io.js:7`), имя файла жёстко содержит `PROM` (`BLOCK`, `game_fill_ui.js:1402`). README говорит «CSV **по умолчанию** — PROM», но выбрать другой стенд нельзя.
- Два похожих фильтра: «Среда» (ПРОМ/ТЕСТ по `vid`/`TARGET_TYPE`, `game_fill_filters.js:329-338`) и «Стенд» (PROM/PSI). Названия легко перепутать.

**Рекомендация:** описать модель стендов (конкурс = объединение строк или отдельное поле — выбрать одно); добавить выбор стенда выгрузки и учитывать его в имени файла; IFT либо поддержать, либо убрать.

### P2-6. `meta()` и поля с одинаковыми ключами
`game_fill_core.js:102-103`

`fieldIndex()` строится заново **при каждом** вызове `meta()`. При промахе по разделу возвращается первое поле с таким ключом. В каталоге общие ключи: `FULL_NAME` (CONTEST/REWARD/INDICATOR), `CALC_TYPE` (CONTEST/INDICATOR/SCHEDULE), `TARGET_TYPE` (CONTEST/SCHEDULE) и другие. Это даёт неверные подписи и варианты, если id раздела передан неточно. Индекс лучше строить один раз при загрузке каталога и не делать неявного перехода к «первому поля с таким ключом».

### P2-7. Архив: частичное восстановление без сохранения
`game_fill_model.js:1363-1381`

При отмене `prompt` посреди `restoreAllFragmentsFromBundle` функция возвращает `false`. Часть фрагментов уже перенесена в живой конкурс, но `persistLocal`/`render` не вызываются: UI не совпадает с данными, а потом это состояние сохранится случайно. Ветка «по типам» (`:1466`) этот случай обрабатывает — выровнять обе ветки.
Выбор при конфликте кода через `prompt("1/2/3")` (`:1160-1174`) неудобен и повторяется для каждой награды — нужен модальный диалог с «применить ко всем».

### P2-8. Копирование конкурса
`game_fill_model.js:741-765`
- Разрешён дубль `CONTEST_CODE` (после `confirm`) — ломает связку архива «по коду» и уникальность в CSV.
- Индикаторы копируются целиком, `INDICATOR_CODE` вида `<старый код>_I1` не переименовывается (переименовываются только `r_`/`t_`).
- Награды `ITEM_…` копируются с тем же кодом: REWARD глобален, поэтому при выгрузке двух конкурсов вторая награда пропадёт (см. P1-1).

### P2-9. Импорт снимка
`game_fill_io.js:300-332`, `:371-376`
- Нет проверки `version` (`PROJECT_JSON_VERSION = 5`) и `catalog_stamp`: файл от другой версии каталога открывается без предупреждения.
- `importProjectText` обращается к `data.contests.length` до проверки — при неверном файле пользователь видит сообщение о TypeError.
- `saveProjectFile` вызывает `revokeObjectURL` сразу после `click()` (`:285`). Для CSV это уже исправлено отложенным revoke (`game_fill_ui.js:1373-1390`), для JSON — нет.

## 4. Архитектура и структура

### 4.1 Глобальное пространство и порядок скриптов
7 файлов объявляют ~60 глобальных `var` и сотни функций. Порядок загрузки в `game_fill_settings.html:286-292` обязателен, но нигде не описан. Зависимости циклические: `core` вызывает `data()`/`cur()` из `model`, `model` использует `sessionReady` из `io` и `pairNavTitle` из `filters`, `io` использует `render` из `ui`. Любое переименование ломает страницу только во время работы.

**Рекомендация:** перейти на ES-модули (`<script type="module">`, работает через тот же `http.server`) с явными `import`. Ориентир — `web-report`, где ядро уже тестируется в Node.

### 4.2 Имена файлов не соответствуют содержимому
| Файл | Заявлено | Фактически ещё содержит |
|---|---|---|
| `game_fill_model.js` | данные, коды, архив | модальные окна копирования и восстановления, **виджеты** (`mountDateUi`, `mountChips`, `mountSearchCombobox`, `mountDropdownCustom`), рендер архива |
| `game_fill_filters.js` | фильтры | `renderFieldCard`, `mountCompositeCode`, вся навигация |
| `game_fill_ui.js` | экраны | **сериализация CSV/SPOD-JSON**, парсинг JSON, упаковка ADD/FEATURE |
| `game_fill_io.js` | JSON/CSV, LS | старт, панели, тултипы, горячие клавиши |

Предлагаемое разбиение:
- `domain/` — чистые функции без DOM: коды, нормализация, стенды, архив, сериализация CSV/JSON;
- `state.js` — состояние сессии и индексы;
- `widgets/` — дата, chips, combobox, общие с web-edit;
- `views/` — экраны;
- `app.js` — привязка событий.

Логику `domain/` можно покрыть node-тестами.

### 4.3 Модель смешана с UI-состоянием
Функции данных меняют глобальные индексы навигации: `applyPairToContest` → `activeLink`/`activeSection` (`game_fill_model.js:1191`, `:1223`); `syncBadgeSlots` → `activeLink`/`activeBadge` (`:2170-2171`); `deleteXAt` → `activeSection`. Из-за этого их нельзя вызвать для неактивного конкурса или в тесте. Нужно: функция возвращает результат, навигацию выставляет вызывающий код.

### 4.4 Нормализация на каждом `render()`
`render()` при каждом вызове выполняет `syncBadgeSlots` + `seedLinked` (`game_fill_ui.js:757-760`); `renderLinkRewardPair`/`renderRewardAdd` — ещё раз. Грязное состояние определяется через `JSON.stringify(всего конкурса)` на каждое изменение (`game_fill_model.js:2199-2202`), baseline «подтягивается», если пользователь ещё не правил (`realignBaselineIfPristine`). Схема хрупкая: любая новая нормализация в рендере может изменить данные незаметно. Нормализация должна выполняться один раз — при импорте или создании.

### 4.5 Раскладки и каталог
- Раскладки (`CONTEST_LAYOUT` и др., `game_fill_core.js:182-281`) и колонки CSV (`:20-25`) заданы вручную в JS. Новое поле каталога попадёт в «Прочее», а в CSV — только если его добавить в `*_COLS` вручную. Порядок колонок и группы лучше хранить в каталоге (`csv_order`, `group`, `span`) — тогда edit будет управлять и формой fill.
- Многострочные поля выбираются по ключам в коде (`game_fill_filters.js:191`) — нужен флаг каталога `multiline`.
- `catalog.js` (128 КБ) загружается всегда, даже если `catalog.json` доступен; при ошибке fetch используется молча (`game_fill_io.js:65-76`). Сейчас они совпадают, но если не запустить sync, откроется устаревший каталог. Стоит показывать источник и штамп заметно, а при расхождении — предупреждать.

### 4.6 Мёртвый код
- `game_fill_app.js` — заглушка «не подключать»;
- `renderTable` (`game_fill_ui.js:685`), `renderBadge`, `renderRewardLink`, `renderContestPeriod` — не вызываются;
- `maxBadges` — синоним `recommendedBadges`;
- `BLOCK` и `projectBlock` дублируют друг друга.

### 4.7 Тесты
Python-тесты (`src/Tests/test_web_fill_*.py`) проверяют скрипты экспорта примеров, но не JS-логику fill. Минимальный набор node-тестов после выделения `domain/`:
- коды: `expandStored*`, `resyncPrefixedCodes`, `uniquifyPrefixedCode` — уникальность, смена CONTEST_CODE, ITEM;
- сериализация: `dumpsSpod`/`csvEscape`/`toCsv` — `;`, переводы строк, кавычки, пустые JSON-режимы;
- `buildTables`: фильтр стендов, целостность пар, дубли;
- импорт → экспорт на `examples/web-fill/contests/*.json` против CSV PROM.

## 5. UX и мелочи (P3)

- Утечка слушателей `keydown` (Escape) в модальных окнах: при закрытии через «Отмена» или клик по фону слушатель не снимается (`game_fill_model.js:444`, `:739`, `:1440`).
- `confirm`/`prompt` — заменить на свои диалоги (они уже есть для копирования).
- Нет предупреждения `beforeunload`, когда черновик не сохраняется (связано с P1-4).
- Нет отмены (undo) для «В архив» и «Удалить безвозвратно».
- Тултип по `mousemove` на весь документ с `getBoundingClientRect` на каждом движении (`game_fill_io.js:463`) — как и в web-edit, лучше `pointerover` + rAF.
- Списки (`kind=list`) с ≥16 вариантами показываются стеной чипов без поиска (`game_fill_filters.js:163-164`), тогда как README и web-edit обещают combobox от 16.
