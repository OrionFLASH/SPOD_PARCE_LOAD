# web-report — подготовка REPORT из турниров

Полностью локальная веб-страница — без сервера, без интернета, без установки: рядом с `web-edit-full` / `web-fill-full`. Берёт данные по одному или нескольким турнирам — из CSV/Excel вручную или массово из выгрузок `SCHEDULE`/`CONTEST`/`REPORT` — сверяет ФИО со справочником, разрешает дубли и собирает единый **REPORT**: CSV для загрузки в SPOD и XLSX с полной диагностикой.

Это технический справочник (полное описание файлов, модели данных, форматов и правил). Пошаговые сценарии работы — отдельно, в [`Docs/WEB_REPORT_USER_GUIDE.md`](../../Docs/WEB_REPORT_USER_GUIDE.md). История доработок по волнам — [`Docs/PLAN_WEB_REPORT.md`](../../Docs/PLAN_WEB_REPORT.md) и [`Docs/PLAN_WEB_REPORT_TODO3.md`](../../Docs/PLAN_WEB_REPORT_TODO3.md); чеклист — [`Docs/TODO_WEB_REPORT.md`](../../Docs/TODO_WEB_REPORT.md).

## Открытие

Открыть `report_app.html` **двойным кликом** — в браузере откроется страница по адресу `file:///…/common/web-report/report_app.html`. Никакой сервер поднимать не нужно.

Чтение CSV/Excel (`<input type="file">`, SheetJS) и скачивание CSV/XLSX (через Blob-ссылку) — целиком в браузере, без сети, работают под `file://` без ограничений.

Единственное, что не работает под `file://` (и не может — браузер блокирует сетевые запросы к соседним файлам с адреса `file:`): автоматическая подгрузка файла источника/ФИО по сохранённому пути при открытии JSON. Подробности — раздел «Путь к файлу» ниже.

Старт — всегда пустая форма: черновик из `localStorage` не подгружается (турниры появляются только через «Добавить», «Открыть JSON» или «Загрузить списки»). Правая панель фильтров при старте свёрнута, левая (турниры) открыта.

После распаковки `web-report_bundle.zip`: переименовать `*.script` по `ПРАВИЛЬНЫЕ_ИМЕНА.txt`, затем открыть `report_app.html`.

## Модель данных турнира

Каждый турнир в списке слева — объект со следующими полями (создаётся `ReportCore.createEmptyTournament`):

| Поле | Смысл | По умолчанию |
|------|-------|---------------|
| `id` | Внутренний идентификатор строки (не путать с кодом турнира) | генерируется |
| `contest_code` | Код конкурса (`CONTEST_CODE`) | пусто |
| `tournament_code` | Код турнира (`TOURNAMENT_CODE`) | пусто |
| `full_name` | Название турнира → в XLSX колонка `CONTEST-DATA=>FULL_NAME` | пусто |
| `plan_value` | План (строка, целое или с запятой/точкой, знак допустим) | `"0"` |
| `contest_date` | Дата данных, `ГГГГ-ММ-ДД` | сегодня |
| `type_ind` | `TN` (в источнике уже табельный) или `FIO` (в источнике ФИО, ищем по справочнику) | `TN` |
| `period_code` | Код периода — см. раздел «Периоды» | `Y` |
| `column_id` | Колонка источника с ФИО/табельным | пусто |
| `column_fact` | Колонка источника с показателем | пусто |
| `fact_op`, `fact_op_value` | Действие над показателем перед записью в `FACT_VALUE`: `none`/`mul`/`div`/`add`/`sub` и число | `none` / `"1"` |
| `source_file_name` | Имя загруженного файла источника | пусто |
| `source_file_path` | Путь для автозагрузки — см. раздел «Путь к файлу» | пусто |
| `source_file_kind` | `csv` или `excel` | пусто |
| `sheet_name`, `table_start_row`, `table_start_col` | Лист Excel и «угол» таблицы (1-based) | `""`, `1`, `1` |
| `include_in_report` | Участвует ли турнир в проверке/выгрузке | `true` (у турниров из «Загрузить списки» — `false`) |
| `source_error` | Текст ошибки источника (транзитное, не сохраняется в JSON) | пусто |
| `needs_identity_fix`, `copy_lock_code`, `copy_lock_name` | Блокировка копии турнира до смены кода и названия | — |
| `import_status`, `import_warning` | Статус и предупреждение после массовой загрузки из SCHEDULE/CONTEST/REPORT (транзитные, в JSON не сохраняются) | — |

Строка данных турнира (после нормализации, `ReportCore.normalizeTournamentRows`) — отдельная структура с колонками `MANAGER_PERSON_NUMBER`, `CONTEST_CODE`, `TOURNAMENT_CODE`, `CONTEST_DATE`, `PLAN_VALUE`, `FACT_VALUE`, `priority_type`, `FIO`, `ТАБЕЛЬНЫЙ НЕ НАЙДЕН`, `ДУБЛЬ`, `СУММА ПО ТАБЕЛЬНОМУ`, `CSV_ERROR`, `fact_error` и др. — см. `CSV_COLUMNS` / `XLSX_COLUMNS` ниже.

## Периоды

`period_code` — один из: `Y` (турнир года), `Q1`–`Q4` (кварталы), `M1`–`M12` (январь…декабрь), `F` (произвольный). В интерфейсе отображается как «название период + код» (`periodDisplay`).

При массовой загрузке из `SCHEDULE.PERIOD_TYPE` действует словарь (`periodCodeFromScheduleType`, подобран по реальным выгрузкам PROM):

| `PERIOD_TYPE` | Код | | `PERIOD_TYPE` | Код |
|---|---|---|---|---|
| турнир года | `Y` | | турнир 1/2/3/4 квартала | `Q1`–`Q4` |
| турнир января…декабря | `M1`–`M12` | | произвольный | `F` |

Всё, чего нет в словаре (например «турнир 2 полугодия», «март-июль», «турнир 2 месяца», «турнир до конца августа») — уходит в **«Произвольный» (`F`)**, турнир при этом помечается предупреждением с исходным текстом периода.

## Формат полей выгрузки

Согласовано с заказчиком:

| Поле | Формат |
|------|--------|
| `MANAGER_PERSON_NUMBER` | ровно 20 цифр, дополнение нулями слева; не найден в справочнике (режим FIO) → `00000000`, тоже дополняется до 20 |
| `PLAN_VALUE`, `FACT_VALUE` | целая часть, точка, ровно 5 знаков (`100` → `100.00000`); округление до 5 знаков, половина — от нуля; отрицательные значения допустимы (`-10.50000`) |
| `CONTEST_DATE` | `ГГГГ-ММ-ДД` |
| `priority_type` | всегда `1` |

**Разбор чисел** (план, показатель, число операции; `ReportCore.parseNumberStrict`): знак `+`/`-`/`−`; пробел или неразрывный пробел — разделитель тысяч; одиночная запятая или точка — дробная часть; если есть и запятая, и точка — дробный тот, что правее (`1.000,25` и `1,000.25` — оба `1000.25`); несколько одинаковых разделителей подряд — тысячи (`1.000.000` → `1000000`); суффикс `%` — делится на 100; пустая ячейка → `0`; всё, что не разбирается как число (`н/д`, `10 руб`, `1,2,3`) — **ошибка**, не `0`.

**Нечисловой показатель** не превращается в 0: `FACT_VALUE` остаётся пустым, в `CSV_ERROR` — «показатель не число: «…»», CSV блокируется, строка считается ошибкой в карточке турнира. План и число операции над показателем должны разбираться как число, иначе поле подсвечено и турнир не считается «заполненным» (кнопки «Проверить»/«Сформировать» неактивны).

**Табельный номер:** причина отказа конкретная (`ReportCore.personNumberProblem`) — пуст, содержит не только цифры, длиннее 20 цифр, или в экспоненциальной записи (`1.23457E+19` — типичный симптом, что колонка табельных в Excel имеет числовой формат; нужно поставить текстовый). Окно «ФИО не найдены» принимает только цифры, не длиннее `person_number_length` (20).

**Excel (чтение):** числовые ячейки (кроме дат) читаются исходным значением, без формата отображения — `0.123456` при формате `0.00` не станет `0.12`, `50%` прочитается как `0.5`. Числа от `1e15` (например, испорченный длинный табельный, потерявший точность в Excel) читаются как текст ячейки, чтобы ошибка была видна, а не терялась молча.

**Excel (запись):** колонки из `ReportCore.PERSON_NUMBER_COLUMNS` (сейчас — только `MANAGER_PERSON_NUMBER`) в выгружаемом XLSX всегда пишутся текстом (`t:"s"`, формат ячейки `@`) — независимо от того, числом или строкой было исходное значение. Это защита от потери точности/ведущих нулей у 20-значного ТН в выходном файле и не зависит от формата столбца в исходном файле (`ReportIO.forcePersonNumberColumnsAsText`, применяется в `ReportIO.buildReportXlsxWorkbook`).

**Excel (много листов):** при разборе книги (`parseExcelWorkbook`) и при каждой смене листа/угла (`applyPackOrigin`) таблица `{rows, columns}` строится только для **одного** — выбранного — листа; остальные листы держатся как сырой AOA (`pack.sheetsAoa`) и превращаются в таблицу лениво, только когда до них дойдёт очередь (пользователь выберет этот лист). До 26.53 таблица пересчитывалась для всех листов книги на каждую смену угла/листа, хотя читался только текущий.

## Колонки CSV и XLSX

**CSV** — только согласованные строки (`include_in_csv !== false`), ровно 7 колонок:

`MANAGER_PERSON_NUMBER`, `CONTEST_CODE`, `TOURNAMENT_CODE`, `CONTEST_DATE`, `PLAN_VALUE`, `FACT_VALUE`, `priority_type`.

Разделитель `;`, кодировка UTF-8 с BOM (для корректного открытия в Excel), строки через CRLF.

**XLSX** — все строки (включая исключённые дублями/ошибками) плюс диагностика:

`MANAGER_PERSON_NUMBER`, `CONTEST_CODE`, `TOURNAMENT_CODE`, `CONTEST_DATE`, `PLAN_VALUE`, `FACT_VALUE`, `priority_type`, `CONTEST-DATA=>FULL_NAME`, `PERIOD`, `PERIOD_CODE`, `ДУБЛЬ`, `СУММА ПО ТАБЕЛЬНОМУ`, `В ФОРМАТЕ`, `PLAN_VALUE_число`, `FACT_VALUE_число`, `FIO`, `ТАБЕЛЬНЫЙ НЕ НАЙДЕН`, `КОММЕНТАРИЙ_ДУБЛЬ`, `CSV_ERROR`.

Лист `REPORT`: закреплена первая строка, включён автофильтр, автоширина колонок.

## Проверки перед выгрузкой (CSV-гейты)

`ReportCore.validateCsvExportRows` блокирует CSV (но не XLSX — там строки просто помечаются в `CSV_ERROR`), если есть хотя бы одна строка с:

- **дублем ключа** `CONTEST_CODE + TOURNAMENT_CODE + MANAGER_PERSON_NUMBER` (после разрешения дублей через диалог — см. ниже);
- **неверным табельным** — не 20 цифр (с конкретной причиной, см. выше);
- **нечисловым показателем**;
- **пустой ячейкой** любой из 7 CSV-колонок.

Модальное окно при блокировке показывает сводку по турнирам (сколько дублей / плохих ТН / плохих показателей / пустых ячеек в каждом) и до 10 примеров конкретных причин.

## Дубли: пайплайн проверки

Проверка (`runValidationPipeline`) идёт по шагам, каждый — с диалогом при необходимости:

1. **ФИО без табельного** (только режим FIO) — окно «ФИО не найдены»: можно дописать табельный (только цифры, до 20 знаков) прямо в диалоге — тогда запись попадёт в справочник — или продолжить с `00000000`.
2. **Дубли по ключу «конкурс + турнир + ФИО»** (только строки режима FIO, до подстановки табельного).
3. **Дубли по ключу «конкурс + турнир + табельный»** (после подстановки, с учётом решений по шагу 2).

Для каждой группы дублей на шагах 2–3 — диалог с решением:

| Режим | Что происходит |
|---|---|
| `keep_selected` / `keep_one` | В CSV остаётся одна отмеченная строка (по умолчанию — первая); остальные исключаются (`include_in_csv = false`) |
| `sum` | Показатели группы суммируются в первую строку, остальные исключаются |
| `drop_all` | Все строки группы исключаются из CSV (в XLSX останутся с пометкой) |
| `abort` | Проверка останавливается без изменений |

Решения запоминаются по «отпечатку» строки (`rowFingerprint`) и переиспользуются при повторной проверке — диалог сразу показывает, что было выбрано в прошлый раз.

## Справочник ФИО

Общий для всей страницы (`state.fioEntries`/`state.fioPack`/`state.fioUi` в `report_app.js`, `fio` — один top-level ключ в JSON настроек, см. ниже) — **не привязан к конкретному турниру**. UI — отдельная модалка `#modal-fio-dict`, открывается кнопкой **«Справочник ФИО»** на левой панели (`btn-fio-dict`); кнопка активна, если хотя бы один турнир в списке (`state.tournaments`) имеет `type_ind === "FIO"` (`hasAnyFioMode()`, пересчитывается в `renderStages()` при каждом изменении списка), независимо от того, какой турнир сейчас открыт в центре страницы. Загруженный в модалке справочник участвует в проверке/формировании сразу у всех турниров FIO — `ReportCore.buildFioMap(state.fioEntries)` строится один раз и передаётся в `normalizeTournamentRows` для каждого турнира.

До волны 26.51 этот же блок рендерился внутри карточки турнира и был виден, только когда выбранный турнир был в режиме FIO — из-за этого казалось, что справочник «свой» у каждого турнира, хотя данные (`state.fioEntries`) уже тогда были общими на все турниры. Вынос в отдельную модалку ничего не меняет в данных или в JSON — только делает общий характер справочника явным в интерфейсе.

Хранится как `{ fio, person_number }[]` в состоянии страницы; можно вести вручную (JSON), пополнять из окна «ФИО не найдены» или собрать из таблицы (`ReportCore.resolveFioTableEntries`):

- при «Применить» из загруженной CSV/Excel таблицы дубли по колонке ФИО разрешаются так: берётся **первая сверху** строка, у которой табельный **не пуст и состоит только из цифр** (ведущие нули допустимы);
- если ФИО встречается один раз — берётся как есть, даже с пустым или нечисловым табельным;
- пользователю показывается предупреждение и кнопка «Подробнее» — модалка со всеми проблемными строками (ФИО, значение, причина, отметка «выбрана»).

Пример таблицы: `examples/sample_fio_dictionary.csv`. Пример готового справочника: `examples/fio_dictionary_example.json`.

### Путь к файлу

Поля «Путь к файлу» (источник турнира и таблица ФИО) — **информационные, только для чтения**; вручную не редактируются. При ручной загрузке файла браузер отдаёт только его имя (реальный путь в файловой системе ОС странице недоступен) — это имя и сохраняется как путь.

**Автоматически подтянуть файл по этому пути при открытии JSON страница не может** — она открыта локально (`file://`), а браузеры не позволяют странице с адреса `file:` делать сетевые запросы к соседним файлам (это ограничение безопасности браузера, не этой страницы). Поэтому после «Открыть JSON» источники турниров всегда приходится загружать вручную заново, даже если путь был сохранён в прошлый раз. Поле остаётся просто подсказкой, каким файлом был этот источник раньше.

Справочник ФИО — исключение: `fio.entries` хранит сами записи (не путь к файлу), поэтому он восстанавливается из JSON целиком без ручной загрузки. «Путь к файлу»/«Имя файла» в блоке ФИО в этом смысле не «источник истины», а просто память о том, какой файл когда-то использовался для сборки текущих `entries` — обновляется только при следующей загрузке таблицы через «Справочник ФИО».

В коде вся механика автозагрузки по пути (`ReportIO.tryReadTableFromPaths`, кандидаты путей, `source_file_path`/`fio.file_path` в схеме JSON) сохранена как задел: если страницу когда-нибудь снова откроют через веб-сервер (`isLocalFileProtocol()` вернёт `false`), автозагрузка заработает сама, без правок кода.

## Загрузка турниров из SCHEDULE + CONTEST + REPORT

Кнопка **«Загрузить списки»** на левой панели открывает модалку в два шага:

1. **Файлы** — три CSV: `SCHEDULE` и `CONTEST` обязательны (проверяются на нужные колонки), `REPORT` — нет (без него дата турниров = сегодня).
2. **Статусы** — уникальные значения `SCHEDULE.TOURNAMENT_STATUS` чипами с множественным выбором и счётчиком строк; «Отметить все» / «Снять все»; живой счётчик подходящих строк. Если `REPORT` загружен, тут же — переключатель «Какие турниры брать»: **«Все»** (по умолчанию, только по статусу) или **«Только из REPORT»** — оставить лишь турниры, для которых в `REPORT` уже есть хоть одна строка (по `TOURNAMENT_CODE`); без загруженного `REPORT` переключатель не показывается.

Сборка турнира из одной строки `SCHEDULE` с выбранным статусом (`ReportCore.buildTournamentsFromSourceFiles`):

| Поле турнира | Источник | Если не найдено / не число |
|---|---|---|
| `tournament_code`, `contest_code` | `SCHEDULE.TOURNAMENT_CODE` / `CONTEST_CODE` | без кода турнира строка пропускается |
| `period_code` | `SCHEDULE.PERIOD_TYPE` через словарь периодов | «Произвольный» (`F`) |
| `full_name`, `plan_value` | `CONTEST.FULL_NAME` / `PLAN_MOD_VALUE` по `CONTEST_CODE` | конкурс не найден → имя пустое; план пуст/не число → `0` |
| `contest_date` | самая новая `REPORT.CONTEST_DATE` для этого `TOURNAMENT_CODE` | нет строк в REPORT → сегодняшняя дата |
| `type_ind` | всегда `TN` (источник данных по участникам подключают отдельно, обычным путём) | — |
| `include_in_report` | всегда `false` — включают вручную, после проверки параметров и загрузки источника | — |

Строка попадает в сборку, только если сначала прошла фильтр статуса, а затем — если включено «Только из REPORT» — фильтр присутствия в `REPORT`; оба фильтра применяются раньше проверки на дубль с уже существующими турнирами. Уже существующие в списке коды турниров при повторной загрузке пропускаются (не дублируются). Турнир с любым отклонением получает `import_warning`: в списке слева — фиолетовая рамка и метка «! СПИСКИ» с причиной в подсказке.

Файл REPORT, если он был загружен на этом шаге, запоминается целиком в `state.importedReportPack` (не только использованные для дат строки) — он нужен позже для кнопки «Обновить REPORT» (ниже). Хранится только в памяти страницы на время сессии — не в JSON настроек, не в `localStorage`.

## Обновить REPORT (пятая кнопка выгрузки)

Дополнительный вариант сохранения — рядом с CSV/XLSX на левой панели, кнопка **«Обновить REPORT»**. Смысл: не просто выгрузить CSV с нуля, а *обновить* уже существующий REPORT-файл — заменить в нём данные по турнирам, которые сейчас готовы к выгрузке, не трогая всё остальное (другие турниры, историю, всё, что не пересчитывалось в этой сессии).

**Доступна, когда:**
- на левой панели уже был загружен REPORT через «Загрузить списки» (`state.importedReportPack` не пуст);
- «Сформировать» выполнено и CSV **реально** готов к скачиванию — гейт зелёный (`state.lastResult.csvGate.ok`), а не просто кнопка CSV не серая (та disabled лишь при отсутствии `lastResult`, но клик может упереться в блокировку — «Обновить REPORT» требует именно пройденного гейта).

**Как считается предпросмотр** (`ReportCore.buildReportUpdatePreview`): готовые к выгрузке строки (`prepareExportRows().csvRows`) группируются по `TOURNAMENT_CODE` — это и есть турниры-кандидаты на обновление (раз CSV-гейт зелёный, у ВСЕХ включённых турниров все строки чистые, так что кандидат — каждый турнир, по которому в этой сессии реально есть готовые строки). Для каждого — сравнение с тем, что было в `TOURNAMENT_CODE` внутри `importedReportPack` (по `MANAGER_PERSON_NUMBER`):

| Колонка предпросмотра | Смысл |
|---|---|
| Было строк | строк этого турнира в загруженном REPORT до обновления |
| Станет | строк этого турнира в новых готовых данных |
| Ушло табельных | были в REPORT, в новых данных для этого турнира их нет |
| Осталось | были и остались (совпали по `MANAGER_PERSON_NUMBER`) |
| Новых | появились впервые, в исходном REPORT их не было |

Турниры, для которых сейчас нет готовых строк (не сформированы, выключены, или просто не участвовали в этой сессии), в предпросмотре не показываются и **не трогаются** — их данные в REPORT остаются как были.

**Выбор турниров.** Перед подтверждением — таблица по турнирам с чекбоксами (по умолчанию отмечены все), «Отметить все» / «Снять все». **«Обновить и скачать»** применяет замену (`ReportCore.applyReportUpdate`) только по отмеченным турнирам: их прежние строки в REPORT удаляются целиком и заменяются новыми; всё остальное — нетронуто. Новый файл скачивается с именем по шаблону `REPORT_<таймштамп>.csv` (`ReportIO.timestampName`), тем же форматом, что и обычный экспорт CSV.

После скачивания `state.importedReportPack` обновляется до результата слияния — повторное «Обновить REPORT» в этой же сессии (например, после донастройки ещё нескольких турниров) работает уже поверх только что обновлённого файла, а не поверх исходного.

## Фильтры и поиск (правая панель)

Четыре независимых блока чипов (пересечение всех условий, «И»):

| Блок | Варианты |
|---|---|
| Тип расчёта | `TN`, `FIO` |
| В выгрузке | Включены / Выключены (по `include_in_report`) |
| Готовность | Готовые / Неполные / Копии (турниры, исключённые из выгрузки, показываются всегда, пока включён хотя бы один из этих трёх) |

Поиск — по каждому полю (код конкурса, код турнира, название, тип, период) отдельно, тремя режимами на выбор:

- **Содержит** (по умолчанию) — совпадение в любом месте поля;
- **Начиная с** — совпадение с начала **слова** внутри поля (не только с начала всей строки): «прод» находит «Продажи» и в «Герой продаж»;
- **Целиком** — поле равно введённому тексту полностью.

## Настройки страницы

Не отдельный `config.json`, а объект `DEFAULT_CONFIG` прямо в `report_app.js` (`fetch` к соседнему файлу под `file://` браузер бы заблокировал — незачем было бы держать значения отдельно от кода). Чтобы поменять — править `DEFAULT_CONFIG` в `report_app.js` и пересобрать `web-report_bundle.zip`.

| Ключ | Назначение |
|------|------------|
| `person_number_length` | Длина табельного номера в выгрузке (20) |
| `number_decimals` | Знаков после точки у `PLAN_VALUE`/`FACT_VALUE` (5) |
| `priority_type` | Значение колонки `priority_type` в выгрузке ("1") |
| `missing_person_placeholder` | Заглушка табельного, если ФИО не найдено в справочнике ("00000000") |
| `no_duplicate_mark` | Прочерк для служебных колонок без значения ("-") |
| `missing_fio_flag` | Значение колонки «ТАБЕЛЬНЫЙ НЕ НАЙДЕН» ("ДА") |
| `csv_delimiter` | Разделитель CSV (";") |
| `csv_encodings` | Порядок кодировок для распознавания CSV (`utf-8`, `windows-1251`, `ibm866`) — строгий UTF-8 (с BOM или без) пробуется первым |
| `preview_row_limit` | Макс. строк в превью источника/ФИО (100) |
| `local_storage_*` | Ключи `localStorage` (черновик на старте не подгружается, см. «Открытие») |
